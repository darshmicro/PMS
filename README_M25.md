No new model or table - like Dashboards (M24), this module aggregates `Employee_Performance`
live (plus `Rating_Master` for the rating label). It is small by design, and the reason is in the
spec's own build-sequence note (Section 10): *"M25's Excel export endpoints (Sec 36A) added
incrementally as each stage module ships, not deferred to the end."* Every module since M3 has, in
fact, shipped its own `GET .../export` endpoint using `export_service.build_export_workbook()` as
it was built - **26 export endpoints already exist across M3-M24** by the time this module starts.
So M25 does not rebuild those. It adds exactly the two things no earlier module had reason to
build on its own.

## Design decisions

**A catalog, not a 27th duplicate export mechanism.** Section 7's screen #38, "Reports & Export
Center (stage-wise export UI per Sec 36A)," needs one place that lists every export the *caller*
can actually reach - not a UI that already has to know 26 endpoint paths and guess which ones a
given role is allowed to call. `REPORT_CATALOG` is a static registry (one entry per existing
export, naming the exact `PermissionCode` that already gates it - the RBAC matrix's own note that
"every row's export permission mirrors its View scope" is taken literally: this catalog invents no
new access rule, it only surfaces what each module already enforces), and `GET /reports/catalog`
filters it down to whatever the caller's own `ctx.permission_codes` already contains.

**One genuinely new report - the first multi-record export in this codebase.** Every one of the 26
existing exports is scoped to a *single* record (one self-assessment, one review, one approval,
one PIP). Nothing before this module produces a "stage-wise" roster across every record a caller
can see at once, which is what the Export Center screen and the build-order table's own "PDF/
Excel/CSV" format list actually imply - a report you'd hand to an auditor or a Plant Head, not a
single form's printout. `build_appraisal_status_rows()` is that report: one row per
`Employee_Performance` in scope, with employee/cycle/status/final score/final rating/lock state.

**Scope reuses M24's `apply_dashboard_scope()` directly rather than re-deriving the same
tiering.** The RBAC matrix's "Reports/Exports" row - `Own | Team-scoped | Dept-scoped | Org-scoped
| Plant-scoped | Org-scoped | Org-scoped | X` - is structurally identical to Dashboards' row, with
one difference: System Administrator gets `X` here (nothing at all), not "system health only." So
this module calls M24's scope function as-is (Plant Head narrowed to Plant, not Org - see that
module's own docstring for why it isn't the shared `BROAD_ACCESS_ROLES` grouping) and simply
raises 403 for `SYS_ADMIN` in the route handler instead of routing it anywhere, matching the
matrix's `X` exactly rather than inventing a consolation view the way Dashboards did for the same
role.

**Three export formats, one new dependency.** The build-order table's own description for this
module is "PDF/Excel/CSV" - Excel was already covered by the existing `build_export_workbook()`
helper (reused as-is for `format=xlsx`), CSV needed only the stdlib `csv` module (`render_csv`),
and PDF needed a real rendering library: `reportlab` (already present in this sandbox and now
pinned in `requirements.txt`) builds a simple, landscape, single-table PDF via
`SimpleDocTemplate`/`Table`, carrying the same "Export Generated By / Export Date-Time / Context"
header block every Excel export already has (spec Section 36A), so the three formats stay visually
consistent with each other and with every prior module's export.

## Business rules enforced (beyond plain aggregation)

| Rule | Where | HTTP result |
|---|---|---|
| `format` must be one of json/xlsx/csv/pdf | FastAPI `Query(pattern=...)` | 422 |
| System Administrator has no access to any report (matrix: X) | `appraisal_status_report` | 403 |
| The catalog only ever lists reports the caller's own permissions already cover | `list_available_reports` | (filtered, not an error) |

## Run tests

```bash
pytest tests/ -v
```

**278 tests total (264 carried over from M1-M24 + 14 new)**, all passing with zero regressions:
unit tests for the catalog's permission filtering, the consolidated report's row-shaping and scope
reuse, and both new renderers producing well-formed CSV text and a real PDF byte stream
(`test_report_service.py`), plus **end-to-end ASGI tests** (`test_report_routes_smoke.py`)
covering the catalog correctly hiding a report the caller lacks permission for, the consolidated
report's JSON/XLSX/CSV/PDF variants (asserting correct `Content-Type` and, for PDF, a real `%PDF`
byte signature), the 422 on an invalid format, Plant Head/HR-style org-wide scoping, and System
Administrator's 403.

Route registration was also verified via `app.openapi()`: **138 total paths** across 30 routers
(up from 136 paths / 29 routers in M24), **164 path+method combinations, zero collisions**.

## What M26+ will build on top of this

M26 (Audit Trail) is next - its own RBAC matrix row already exists too ("Audit Log |
X | X | X | V(dept) | V(plant) | V(all) | V(all) | V(all, no edit)"), and `Audit_Log` itself has
existed as a write path since M1 (`write_audit()`, called by every mutating endpoint in this
codebase). Like this module and Dashboards before it, M26's job is almost certainly the *reader*
- a scoped, filterable viewer over data that already exists - rather than a new write path,
continuing the pattern of M24-M26 being the "consumption" layer over everything M1-M23 already
produced.
